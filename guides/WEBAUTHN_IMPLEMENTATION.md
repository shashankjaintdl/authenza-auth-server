# FIDO2 / WebAuthn — Passwordless Authentication (E2E Implementation)

**Status:** ✅ Fully Implemented (Phase 2)  
**Library:** `com.yubico:webauthn-server-core:2.5.4`  
**Services involved:** `auth-iam-service` (port `8082`) · `auth-server-core` (port `8081`)

---

## Overview

FIDO2/WebAuthn allows users to authenticate using their device biometrics — **no password required**. The private key is generated by the OS and **never leaves the device**. Only a cryptographic signature is sent to the server.

### Supported Authenticators

| Authenticator | Transport | Platform |
|---|---|---|
| Touch ID / Face ID | `internal` | macOS · iOS |
| Windows Hello | `internal` | Windows |
| Android Biometrics | `internal` | Android |
| iCloud / Google Passkeys | `hybrid` | Cross-device sync |
| YubiKey 5C / NFC | `usb`, `nfc` | Hardware key |

### Why Two Services?

The WebAuthn **cryptographic ceremony** (FIDO2 challenge + assertion verification) runs in `auth-iam-service` because that is where the credential database and Yubico library live. But the **OIDC session** (Spring Security `SecurityContext`, session cookie) lives in `auth-server-core`. The **Bridge Token** is the secure handshake that connects them.

### Multi-Tenant Isolation
All credential data is stored in the **tenant's own isolated database** via `RoutingDataSource`. A passkey registered for Tenant A **cannot** be used or seen by Tenant B — this is structurally enforced, not just a query filter.

## Database Schema (V0.0.11 Migration)

```sql
CREATE TABLE webauthn_credential (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id       BIGINT        NOT NULL,            -- FK → application_user.id
    credential_id VARCHAR(1024) NOT NULL UNIQUE,     -- FIDO2 Credential ID (base64url)
    public_key_cose TEXT        NOT NULL,            -- COSE public key bytes (base64url)
    sign_count    BIGINT        NOT NULL DEFAULT 0,  -- Replay-attack counter
    display_name  VARCHAR(255),                      -- User label: "My iPhone"
    aaguid        VARCHAR(64),                       -- Authenticator model GUID
    transports    VARCHAR(255),                      -- ["internal"], ["usb","nfc"], etc.
    user_verified BOOLEAN       NOT NULL DEFAULT 0,  -- Was biometric/PIN used?
    created_at    DATETIME      NOT NULL,
    last_used_at  DATETIME,
    INDEX idx_webauthn_user_id (user_id)
);
```

## API Reference

### Base URL: `http://localhost:8082` (auth-iam-service)

---

### Flow 1 — Passwordless Login (Unauthenticated)

Called from the login page **before** the user has a session.

---

#### `POST /webauthn/authenticate/start`

Generates a WebAuthn assertion challenge. Returns the credential options JSON for the browser's `navigator.credentials.get()` call.

**Auth:** None  
**Request Body:**
```json
{ "username": "user@acme.com" }
```

**Response `200 OK`:**
```json
{
  "status": 200,
  "message": "WebAuthn authentication challenge generated.",
  "data": {
    "credentialCreationOptions": "{\"challenge\":\"Yjk4ZmFh...\",\"timeout\":60000,\"rpId\":\"localhost\",\"allowCredentials\":[{\"type\":\"public-key\",\"id\":\"Yjk4ZmFh...\",\"transports\":[\"internal\"]}],\"userVerification\":\"required\"}",
    "requestId": "661f9511-f30c-52e5-b827-557766551111"
  }
}
```

**Error `404`:** User not found (no account with that username/email).

---

#### `POST /webauthn/authenticate/finish?tenantId={tenantId}`

Verifies the signed assertion from the device. On success, issues a **short-lived (60-second) HMAC-signed bridge token** containing the verified userId and tenantId.

**Auth:** None  
**Query Param:** `tenantId` — the tenant the user is logging into (read from the login page URL)  
**Request Body:**
```json
{
  "requestId": "661f9511-f30c-52e5-b827-557766551111",
  "credentialJson": "{\"id\":\"Yjk4ZmFh...\",\"rawId\":\"...\",\"response\":{\"authenticatorData\":\"...\",\"clientDataJSON\":\"...\",\"signature\":\"...\",\"userHandle\":\"000000000000002a\"},\"type\":\"public-key\"}"
}
```

**Response `200 OK`:**
```json
{
  "status": 200,
  "message": "Passkey authentication successful.",
  "data": {
    "userId": 42,
    "tenantId": "acme",
    "bridgeToken": "dXNlcklkPTQyJnRlbmFudElkPWFjbWUmZXhwPTE3NDY0NzY0MDA.HMAC_SIGNATURE"
  }
}
```

**Error `400`:** Assertion signature invalid, sign count backwards (cloned key), or challenge expired.

> **Security Note:** The `bridgeToken` is a compact `payload.signature` string where the payload is base64url-encoded `userId:tenantId:expiryMs` and the signature is HMAC-SHA256 computed with a shared secret. It expires after **60 seconds** and is single-use.

---

### Base URL: `http://localhost:8081` (auth-server-core)

---

#### `POST /{tenantId}/webauthn/bridge`

**The Bridge Endpoint** — completes the OIDC login on the auth server side.

The login page JavaScript submits this as a **hidden form POST** (not `fetch`) so the browser correctly receives and stores the Spring session cookie from the redirect response.

**Auth:** None (the bridge token *is* the authentication proof)  
**Form Body:** `application/x-www-form-urlencoded`

| Field | Type | Description |
|---|---|---|
| `bridgeToken` | `string` | The signed token from `/webauthn/authenticate/finish` |

**What it does:**
1. Validates HMAC-SHA256 signature and 60-second TTL
2. Verifies `tenantId` in token matches the URL path variable
3. Reverse-lookups username from `userId` via `JdbcTenantUserDetailsService.loadUsernameById()`
4. Loads full `UserDetails` and checks account is active/not-locked
5. Creates `UsernamePasswordAuthenticationToken` and stores it in `HttpSession`
6. Records the session in `user_session` for Active Devices tracking
7. Redirects to the pending saved OAuth2 `/authorize` request (or `/{tenantId}/`)

**Success:** `302 → /{tenantId}/oauth2/authorize?...` (completes the OIDC code flow)  
**Error:** `302 → /{tenantId}/login?error` (if token invalid/expired) or `302 → /{tenantId}/login?locked`

## The Bridge Token

### Format
```
base64url(userId:tenantId:expiryEpochMs) + "." + base64url(HMAC-SHA256(payload))
```

### Example
```
dXNlcklkPTQyOnRlbmFudElkPWFjbWU6ZXhwPTE3NDY0NzY0MDA.Tm9uZS1jb25zdGFudC10aW1l
└────────────── payload (base64url) ────────────────┘   └───── signature ──────────┘
```

### Security Properties

| Property | Detail |
|---|---|
| **60-second TTL** | Tokens expire quickly — cannot be replayed after the window |
| **HMAC-SHA256** | The shared secret is never transmitted; only the signature is sent |
| **Tenant binding** | `tenantId` is baked into the payload and verified on both sides |
| **Constant-time compare** | Signature comparison uses `^` XOR to prevent timing attacks |
| **Single-use (recommended)** | Add Redis set-tracking in production to reject replayed tokens |

### Shared Secret Configuration

Both services must have the **identical** `bridge-secret`:

```yaml
# auth-server-core/application.yaml AND auth-iam-service/application.yaml
app:
  webauthn:
    bridge-secret: "a3f8e1d2c4b5a6f7..."   # hex-encoded 32 bytes
    # Generate: openssl rand -hex 32
```

## Security Design

### Replay Attack Prevention (Sign Counter)
Every time a hardware authenticator signs a challenge, it increments an internal counter (`sign_count`). The server stores the last known value. If the server receives a **lower or equal** count, it means the key was **cloned** — the Yubico library automatically throws `AssertionFailedException`.

> **Note:** Software-based authenticators like iCloud Keychain and Google Password Manager always send `sign_count = 0`. The Yubico library handles this by treating count = 0 as "not enforced" for these authenticators.

### Challenge Binding
Both challenge maps use a 5-minute TTL `ConcurrentHashMap`. A challenge can only be used once — it is **removed from the map** before verification starts (`getAndRemovePending`).

### Tenant Isolation
`TenantAwareCredentialRepository` wraps `WebAuthnCredentialRepository`, which is backed by the per-tenant `RoutingDataSource`. The `RelyingParty` can only find credentials that exist in the currently active tenant's DB.

## Login Page UX

The "Sign in with Passkey" button is automatically **hidden** on browsers that don't support WebAuthn (`window.PublicKeyCredential` check). On supported browsers it appears below the password form with an "or" divider.

**UX States:**

| State | Message shown |
|---|---|
| No username entered | "Please enter your username or email first." |
| Challenge generated | "Starting passkey authentication…" |
| Awaiting biometric | "Waiting for your device biometric…" |
| Verifying | "Verifying passkey…" |
| Redirecting | "Signing you in…" (green) |
| User cancelled dialog | "Passkey authentication was cancelled." (red) |
| Server error | Error message from API response (red) |

## Configuration Reference

### `auth-iam-service/application.yaml`
```yaml
app:
  webauthn:
    rp-id: "localhost"              # Effective domain — no port, no scheme
    rp-name: "Authenza"            # Shown in OS biometric prompt
    origin: "http://127.0.0.1:4200"  # Exact browser origin of login page
    bridge-secret: "<hex-32-bytes>"  # MUST match auth-server-core
  auth-server:
    base-url: "http://localhost:8081"
```

### `auth-server-core/application.yaml`
```yaml
app:
  webauthn:
    bridge-secret: "<hex-32-bytes>"  # MUST match auth-iam-service
  services:
    iam:
      base-url: http://localhost:8082
```

> **Production:** Set `rp-id` to your auth server's effective domain (e.g., `auth.authenza.com`). Set `origin` to the browser URL where the login page is served. Both must be consistent — browsers enforce this strictly.

## Next Steps (Production Hardening)

1. **Redis challenge store:** Replace the in-memory `ConcurrentHashMap` with a Redis `SET` for cluster-safe challenge state sharing and automatic TTL eviction.
2. **Bridge token single-use enforcement:** Store consumed bridge tokens in Redis with a 60-second TTL. Reject any token seen more than once.
3. **Discoverable credentials (usernameless login):** Set `ResidentKeyRequirement.REQUIRED` and allow `navigator.credentials.get()` without an `allowCredentials` list — the browser can pick the passkey automatically from a passkey manager (iCloud Keychain, Google Password Manager).
4. **MFA + Passkey policy:** Add a tenant setting to allow passkey login to **bypass TOTP MFA** (since biometric IS a second factor by definition). Toggle per tenant in Phase 4.
5. **Passkey attestation verification:** Enable attestation trust anchors (FIDO MDS3 metadata service) to verify the authenticator model and reject untrusted devices for high-security tenants.
